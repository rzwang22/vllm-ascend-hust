# P08-R5：DSA shared-KV 校验与 ACLGraph capture

## 基线与首错

plugin `9c0d39237938b7ba26ddcb1fa08bdda1a54c4b45`；
core `897306c43bf800e2480cb5c0f3e2da408d85a2fd`。
按本轮服务器报告，SOURCE/DATASET/FOCUSED 已通过，capture warmup 已通过，
首错在实际 `torch.cuda.graph` 区间内的 shared-KV `_assert_async`。
不能把这次错误再归为 R4 dummy slot，也没有正式 FULL replay 成功的证据。
本次只在 Mac 修改和检查，没有连接服务器；历史附件只作为证据读取。

历史 R3 日志记录 Torch `2.10.0+cpu`、torch_npu `2.10.0.post2`。
本轮未收到可核对当前二进制的新归档，因此以下区分上游源码审计和实际服务器观察：

- PyTorch 2.10 的 `_assert_async` 两个 overload 只列出 CPU/CUDA dispatch；
  CPU 实现调用 `is_nonzero`，名称中的 async 不保证 NPU 异步执行。
  见 [2.10 dispatcher 定义](https://github.com/pytorch/pytorch/blob/v2.10.0/aten/src/ATen/native/native_functions.yaml)
  和 [CPU 实现](https://github.com/pytorch/pytorch/blob/v2.10.0/aten/src/ATen/native/TensorCompare.cpp)。
- Ascend 公开源码 `70a8d76d` 的 NPU native 注册中未找到 `_assert_async`；
  PrivateUse1 未注册算子可进入 `at::native::cpu_fallback`。
  PyTorch 的 CPU fallback 会先将设备 tensor 转到 CPU。
  见 [NPU fallback](https://github.com/Ascend/pytorch/blob/70a8d76db5c125189b6322895e6e77b008c96899/torch_npu/csrc/aten/VariableFallbackKernel.cpp)
  和 [2.10 CPU fallback](https://github.com/pytorch/pytorch/blob/v2.10.0/aten/src/ATen/native/CPUFallback.cpp)。
- NPU `LocalScalarDense` 也明确包含 stream synchronize 和 D2H memcpy；
  换成设备 tensor 的 `.item()` 或 Python bool 同样不是 capture 修复。
  见 [标量读取实现](https://github.com/Ascend/pytorch/blob/70a8d76db5c125189b6322895e6e77b008c96899/torch_npu/csrc/aten/common/LocalScalarDenseNpu.cpp)。

上述源码解释与报告的 memcpy 107030 / captured-stream synchronize 107027 一致，
但公开源码 SHA 不等于服务器 wheel 的构建 SHA，不能据此声称已实测该 wheel 的 dispatcher。
新脚本会记录实际 Torch/torch_npu 版本及 `aten::_assert_async.msg` dispatch table，供复测核对。
修复不依赖该算子在 NPU capture 中可用。

## 校验位置与生命周期

production 修改限于 `attention/dsa_v1.py`、`worker/v2/model_states/default.py`、
`worker/v2/aclgraph_utils.py`。不修改 core/custom op、模型、配置构造或采样。

| 检查 | 执行位置 |
| --- | --- |
| KV rank、block size、shape、stride、storage bounds、alignment、dtype/device、metadata dimensions | 原 page validator 的 forward 入口保留；均为 host 可读的 tensor 属性 |
| query 与 KV 的 shape/dtype/device、sink shape | 原 query validator 保留 |
| query 起点为 0、实际 query 行严格递增、末端等于 query token 数 | 每次 metadata 构造完成后的 preflight |
| seq lens 包含本轮 query，且不超物理 cache 容量 | 同一 preflight |
| block table 范围、slot block 范围、slot offset 范围 | 同一 preflight；保留 R4 精确 `[-1, block_size-1]` sentinel |

8 个动态 predicate 共用同一实现。eager 继续使用原检查入口；graph target 的
`AscendModelState.prepare_attn` 在 R3 builder 更新常驻 buffer 后检查设备 tensor 的当前值，
通过后才发布本轮验证记录。记录包含实际索引 buffer 的地址、shape、stride、dtype/device、
请求/token 数、block size 和共享层 cache 容量下界。
forward 只在记录与实际消费的 buffer/容量匹配时使用前置结果，静态布局检查照常执行。
未准备记录就进入 NPU capture 会明确报错，不调用不兼容的 assertion，也不切换为 eager。

只选择 `AscendSlidingWindowMLASpec(model_version="deepseek_v4")` 的 DSA SWA group。
compressor state cache 也使用 DSA builder 且 ratio=1，但其 model_version=None，不能当作 ori_kv 校验。
每个 SWA group 使用自己的 block size，并以实际绑定的共享层 KV 容量检查索引。
其他 attention backend、compressor/indexer 的专用 metadata 行为保持原样。

冻结 core 的三条路径如下：

1. capture warmup：`prepare_inputs_to_capture` 调用 `prepare_attn(NONE, for_capture=True)`，
   完成 dummy buffer 更新和本轮 preflight，然后 warmup forward。
2. 实际 capture：core 再次调用 `prepare_inputs_to_capture`，创建新的 metadata/验证记录，
   完成 preflight 后才进入 `torch.cuda.graph`。不能根据 runtime NONE 排除 capture warmup。
3. 正式 replay：core 每步先更新真实 block/slot/input buffer，再调用 `model_state.prepare_attn`，
   然后才调用 `run_fullgraph`。FULL replay 许可绑定本轮 metadata 对象和 padded token 数，
   只允许消费一次；每次新构造先清除旧许可，失败时保持失效。capture 的 dummy 记录不授权正式 replay。

core 在 metadata 构造与 FULL replay 之间没有再次更新 DSA 的这四类索引 buffer；
该边界后的索引写入必须继续经过新的 prepare/preflight。
不依赖 Tensor version counter，因为 inference tensor/Triton 写入不能提供可靠的版本契约。
R3 的 metadata 对象每轮新建，builder 的 slot/SAS/起始位置 buffer 仍原址更新；
本次不替换任何 graph 输入 buffer，也不复用上一轮“已验证”的布尔值授权新输入。
DSpark drafter 的 metadata 从其独立的 eager 构造路径进入，不覆盖 target 的 replay 许可。

## 同步次数与性能限制

本实现**每次 target metadata preparation 有一次显式 D2H 同步**：
把全部动态 predicate 的 bool 结果 stack 后一次回读，而不回读完整索引 tensor。
每个不同的 SWA leaf 为 8 个 bool；同一构造中跨共享层/相同 group 去重，prefill/decode 也合并为一次传输。
48 层共享同一 leaf 的 CPU 测试确认仍只传 8 个 bool。
实际 capture 内、每层 forward 和 graph replay 内不新增 `.cpu()`、`.item()` 或 synchronize。
正式输入更新的 preflight 每步都会执行，不把 warmup 的成功结果用于后续真实输入。
target 的 eager prefill 分支也在构造后检查；独立 enforce_eager 路径保持原实现。

旧 NPU eager 路径可能为同一 leaf 触发 8 次 assertion CPU fallback，本次 graph target 把它们合并。
但旧版本没有成功的 graph replay 基线，因此不能据此宣称 graph 每步成本下降或 NPU 性能已通过。
正式 replay 前的一次同步仍会打断 host/device overlap，Mac CPU 测试不能证明开销不显著。
冻结 core 的 block/slot 当前只在设备端更新，仅检查现成的 CPU query/seq mirrors 会漏掉真实设备索引错误；
不能用这种不完整校验冒充零回读方案。

Graph P1 通过后，需观察 profiler 中 preflight 的 predicate kernels、status copy 和 host 等待，
再做同配置 eager/graph 的端到端延迟、输出吞吐比较。core 的 verification 计时起点在 metadata preparation
之后，单看该局部计时会漏掉 preflight 成本；性能比较必须包含整步/正式生成总时间。
本次不增加跨 mode exact-token 门槛，也不声称已完成 NPU 性能验收。

## 本地验证

在 Mac 的隔离 Python 环境中执行，没有触碰服务器模型或运行环境：

- CPU Torch 2.10.0：R5 capture validation + R4 padding 测试，45 passed / 44 skipped。
  Torch 2.14.0 CPU 也得到相同结果。skipped 为需要安装 vLLM/Ascend 的 imported-class 变体。
- 无 Torch 的 Python 3.12 环境：R1/R2/R3、draft/profile/采样/proposal/KV/benchmark 回归及 R4/R5
  shell 控制流测试共 348 passed / 35 skipped。
- 使用真实源码函数体执行 core dummy(-1) → model state → builder → preflight → validator；
  K=5、B=1/2/4，warmup/capture/replay 轮次、坏索引、精确 padding、buffer identity 均有覆盖。
  两个真实 forward 入口在压缩比 1/4/128 下执行到 NPU prolog 前，validator 没有被 mock。
  KV 写入使用 R4 从真实 C++ 提取的 int32 key 10/11 地址与边界逻辑加 CPU reference，padding 不改写 KV。
- 普通 pytest 启动仍在仓库 conftest 导入时因 Mac 未安装 vLLM 失败，RC=4；未把它算作通过。
  `--noconftest` 源码执行不是 NPU operator/图执行的替代证据。

变更文件的全部 manual hooks、ShellCheck、Bash/嵌入 Python 语法和 `git diff --check` 通过。
按仓库要求在隔离 worktree 运行 `bash format.sh ci`，RC=1：仍有基线 Ruff/格式、证据文件拼写、
markdown、workflow 输入、旧 shell 和 forbidden-import 问题，与 R4 全仓库检查结果一致。

## 服务器 focused + Graph P1

在原已初始化 CANN/custom-op 的容器执行，无需 `build_aclnn.sh`：

```bash
git -C /workspace/vllm-ascend-hust pull --ff-only origin feat/dspark &&
    bash /workspace/vllm-ascend-hust/tools/dspark/run_p08_r5.sh
```

[run_p08_r5.sh](run_p08_r5.sh) 使用全新目录 `/workspace/dspark-results/m2_5a-p08-r5.XXXXXX`，
保存本次脚本、版本/导入位置/dispatcher、数据副本、日志/JSON、各管道 PIPESTATUS、gate 和执行后快照。
固定 TP8/EP、K=5、B=1、capture sizes=[6]、target FULL_DECODE_ONLY、draft eager，
沿用 R3 token-ID dataset 并核对 SHA256；不删除旧目录或失败产物。
脚本没有 `set -e`/`exit`，每条管道立即保存 PIPESTATUS；失败后 return 阻止依赖步骤继续。

JSON gate 要求 capture 成功、**正式生成 measured FULL replay > 0**、正式记录的
padded/unpadded verification tokens 均为 6、真实 drafts > 0，以及 engine shutdown 完成。
只有 warmup/capture 记录或 NONE 执行不能通过。P1 通过后再继续 B=2/4（对应 query tokens 12/24
需要匹配 capture 覆盖），随后进行上述同配置 eager/graph 性能比较。
