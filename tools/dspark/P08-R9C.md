## 从构造到 kernel 的闭环

1. `patch_v2/patch_input_batch.py` 将 core capture 路径的 InputBatch 指向 AscendInputBatch。
   冻结 core `prepare_inputs_to_capture()` 调用该 make_dummy。
2. core `InputBatch.make_dummy()` 原本返回 runner InputBuffers 的 tensor views。
   plugin 用 `asdict(input_batch)` 构造派生 batch；该 API 递归 deepcopy tensor。
3. `AscendModelState.prepare_attn()` 将 batch.seq_lens/query_start_loc/positions 传给
   `build_attn_metadata()`；DSA builder 再通过 slice 将 seq_lens 直接放入 decode metadata。
   captured 对象因而强持独立的 dummy storage。
4. 正式 `NPUModelRunner.prepare_inputs()` 的 `prepare_pos_seq_lens()` 写入
   `self.input_buffers.seq_lens/positions`，query offsets 也更新 runner buffer。
   此后 prepare_attn 构造 current metadata，更新持久 SAS/start_pos/slot/block/RoPE buffers。
   这些更新不会写回已经深拷贝的 captured seq_lens。
5. `DeepseekV4Attention.forward()`→`AscendDeepseekSparseAttention.forward()`→
   `torch.ops.vllm.dsa_forward`→`AscendDSAImpl.forward()`→`_forward_decode()`。
   layer.1 只持 SWA metadata，走 compress_ratio≤1 分支；KV 来自该 layer 的 swa_cache owner。
6. `_forward_decode()` 将 `common_decode_metadata.seq_lens` 原样传作
   `npu_sparse_attn_sharedkv(..., seqused_kv=..., layout_q="TND", layout_kv="PA_ND")`。
   910B2 的 DeviceOperator 选择普通 sharedkv/scatter 分支，非 A5 quant-sharedkv 分支。
7. kernel `arch32/sparse_attn_sharedkv_swa_kernel.h` 的 `Init()` 对 TND/PA_ND 调用
   `InitActualSeqLen(cuSeqlensQ, seqUsedKV)`；`GetActualSeqLenKV()` 读取该设备 tensor，
   并在主循环据此计算 `actOriS2Size` 与 SWA mask 左右边界。这不是未被使用的 Python 字段。

rank 0 具体存储证据（64/65/66 内稳定）：current seq_lens storage=`20623359467520`，
captured storage=`20775830658560`；captured 始终 `[6,6,6,6]`。
current/captured query offsets 地址也不同，只是此 B4 固定形状的值恰好相同。
start_pos、slot_mapping、block_table、SAS/QLI 则为持久共享 storage，内容同步更新。
因此旧图混合使用新 SAS/slot/block 数据与旧 seqused_kv；前两轮输出有限不能证明这组输入合法。
CPU 回归执行真实 core/plugin 构造方法、真实 `_forward_decode()`，保留 leaf 实参引用后更新 runner buffer，
无需再次 Python forward 即可复现旧引用停留在 dummy 长度的问题。

## positions 全零与 attention 内部范围

captured input_positions 也是 deepcopy 的结果；但不能等同于 layer.1 RoPE 使用零位置。
该层 forward 并不直接消费 metadata.input_positions：它取 `cos[layer_name]`/`sin[layer_name]`。
`rope_dsv4.get_cos_and_sin_dsa(use_cache=True)` 将当前 positions 对应的值 copy 到持久 runtime buffers，
RopeDataProxy 返回这些 buffers 的 views。capture 持有这些 views，prepare_attn 在 replay 前更新其内容。
本包 R9 将 RopeDataProxy 标为非 tensor/unavailable，未记录其最终 leaf tensor 的内容，
所以源码说明更新机制，但包内不能独立证明每次 leaf RoPE 内容正确。

源码默认启用 DSV4 多流 prolog，原命令未覆盖该配置。路径为 Q/KV quant/projection，
aux stream 上 KV norm/RoPE/scatter，主流 wait_stream 后 Q RMS/RoPE，再做 SWA、inverse RoPE、o_proj。
本包没有记录 prolog 分支的运行时标志、Q/KV 中间值、SWA 原始输出及 o_proj 输入；
`layer.1.attn_output` 已包含这些步骤，不能据此直接指认某个量化、scatter 或 attention kernel 产生 NaN。
尤其不能证明旧 mask 实际读取的历史 KV 全部有限，也不能证明本次修复是 NaN 的唯一原因。

## raw slots 与真实 KV owner

layer.1.swa_cache 属于 **group 3**，block size=32。
请求 0 在 64/65/66 按 num_blocks 截取的表前缀均为 `[5,6,7,126,15,76]`。
epoch 66 的 positions 169–174 对应逻辑 column 5、physical block 76、offset 9–14，
raw slots=`2441..2446`，DSA captured slot_mapping=`[76,9]..[76,14]`。
全部 rank、全部三轮按实际 group/idx_mapping 校验均一致；没有该写入的越界证据。

group 0 包含 c4/indexer 压缩缓存，group 1 为 c128 压缩缓存，均不是 layer.1 的 SWA owner。
其表长针对压缩序列，拿未压缩 position//32 索引已分配前缀会超出观测范围。
raw kernel 的实际输出为 position%32；从源码看它仍以未压缩位置读取表容量，
但诊断没有读取这些未分配列，不能把其物理块推定为合法 request KV 或越界写入。
DSA builder 对 compressor_ratio>1 不使用这份 raw slot_mapping，而令其为 None，
forward 的 compressor metadata 路径另行产生真实 scatter slots。

原诊断把字符串 `unavailable: ...` 与整数 actual 比较，制造了确定性的假 mismatch。
本次改为记录 cache owner/spec/block size、unknown 行和检查范围；仅比较期望可确定的行，
padding 仍严格比较 -1，已知物理块/offset 错误仍产生 mismatch。
不会用压缩比任意改写实际 raw slots，也不会扫描表的未分配容量。
