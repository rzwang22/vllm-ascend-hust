## 已证明的检出点与尚未证明的起点

Graph B4 日志第 805 行首个已观察 NaN 来自 TP7：
`sample_tokens → propose → _execute_draft → _execute_sequential_markov_sampling`。
`compute_draft_logits(hidden_states)` 后的 NaN 检查在 Markov 逐位置采样之前；
这只证明检出点，不能证明 LM head 是产生点。
日志中的 `aten::_assert_async.msg` CPU fallback 也不能当作无同步开销的证据。

冻结 core 的 `sample_tokens` 在 target sample/postprocess 后调用 `speculator.propose`；
异步 output 已在此前构造，但新的 DSpark proposal 必须在 draft/Markov 成功后才发布。
`propose` 先消费并释放旧 owner，随后 prepare 新 epoch、执行 draft、最后发布。
NaN 中断发生在新 publication 之前；worker busy loop 仍可能收到已排队的 execute。
这支持随后 `installed proposal tokens without published ownership` 为级联故障，
没有理由放宽 ownership guard。第 1509 行 scheduler dump 的 output counts
`[107,92,118,104]`、每请求 query=6、总 query=24 不能精确映射到首个坏 epoch。

本轮逐项审计了以下真实路径，没有找到可用 CPU 行为证据证明的特定更新遗漏：

| 边界 | 源码事实与归因限制 |
| --- | --- |
| target graph 输出 / aux | 冻结 `ModelCudaGraphManager.capture` 按形状捕获，将输出/aux 写入最大形状的持久 buffer；`run_fullgraph` 返回本次 descriptor 的 prefix view。仅凭共用 storage 不能认定覆盖错误 |
| target 输入 / metadata | `AscendModelState.prepare_attn` 每轮准备 metadata；R3 的三组共享字典是本轮新对象。DSA 的 formatted slots、decode SAS/QLI、start positions 原位更新；core dummy block tables 是实际 input block table 的 view |
| replay / 压缩 metadata | R5 preflight 与本轮 metadata/num_tokens 绑定；DSA `update_graph_params` 是空实现，依靠持久输入。压缩 metadata 在 forward 中消费 start positions、query/block tables、rope；没有证据把约 100 output tokens 等同于某个 block bug |
| hidden bridge | DeepSeek V4 aux 按配置层边界输出；pre-HC MTP buffer 与普通 target hidden 不同。proposal 接收当前 valid prefix，并保持 aux view；诊断分别记录 target output、proposal last hidden 和三组 aux |
| draft context / KV | `prepare_proposal_inputs` 在更新 draft query slots 前 clone context slots，同 group 共享 clone。draft 使用独立 metadata builders；context epoch 在首次写入前消费。`_store_standard_swa_kv` 使用真实 SWA cache block size，经 DSA formatter/scatter 写入 rank-4 paged KV |
| stream / 生命周期 | target graph 返回到冻结 execute/sample 顺序后才进入 eager draft；未发现可证明的缺失 event 契约。没有据此添加默认同步；实际 NPU 时序、kernel 数据与跨 shape 竞争仍待观测 |

一次 Eager B4 成功不能证明 eager 永远正常，也不能唯一锁定 graph kernel。
B2/B4 同时改变并发和生成长度，不能把 batch size 当作唯一触发因素。

## 诊断实现与开销

`--dspark-nan-diagnostic-dir` 是已实现的 benchmark CLI，默认 `None`，仅允许 DSpark + FULL_DECODE_ONLY。
通过 `additional_config.dspark_nan_diagnostic_dir` 传递，没有新增环境变量。
R7 extension 在 capture 完成后的首次边界 RPC 安装诊断，重复安装复用同一实例。
命名 RPC 的可选 `diagnostic_phase` 关键字标记 warmup、measured、complete；仍使用安全字符串 RPC，
不使用 pickle fallback，不新增逐步 RPC。

`DSparkNaNDiagnostics` 按 rank 输出：

- `rank-N-first-failure.json`：独占创建，保留最早检出边界，外层异常不能覆盖。
- `rank-N-latest.json`：原子替换，包含当前轮与最近两轮已复制的主机诊断状态。
- `diagnostic-index.json`：脚本汇总已有文件，缺失 rank 明确列出；不是合并 stdout JSON。

边界依次为 target 输出/aux、当前 proposal 输入、combined context、写入后的 context KV、
eager draft hidden、base logits。每个边界记录 phase、rank、execution/proposal epoch、request IDs、
实际 padded/unpadded shape、query offsets、positions、sequence lengths、有效行范围、dtype/stride/data_ptr，
以及 NaN/+Inf/-Inf 行数和最多 8 个坏行索引，不输出 hidden/logits/KV 的浮点值或权重。
context KV 只检查本轮写入的有效 slots，使用真实 group block size；精确 `-1` 排除读写，
其他负值/越界仍失败；不会扫描未分配 KV 或把 padding 当成真实 request。
base logits 允许合法 mask 的 `-Inf`，保留原有 NaN/Markov/ownership/epoch 校验。

所有新增 tensor reductions、整数诊断拷贝、KV 行选择和 flags D2H 都受显式开关控制，
每个边界先检查 NPU capture 状态，capture/dummy/profile 不安装或不执行本轮诊断。
每步多次同步与文件写入会显著扰动时序，**诊断运行不可用于性能比较**；没有诊断开关时，
仅多出少量 `getattr`/`None` 主机分支，不增加 device sync、D2H 或 tensor 检查。
没有重构原来的 `_assert_async` 系统，也没有把其名字解释为无同步保证。

benchmark JSON 标记 `performance_eligible=false`，保留原始输出和计时作为诊断，
CLI 不打印 benchmark PASS/吞吐摘要，summary 拒绝该文件进入性能比较。
如果 warmup 已异常退出，可能没有完整 benchmark JSON；rank 文件和原始日志仍归档。
即使诊断运行全部有限，也不能证明原问题已消失：同步可能改变原来的竞争时序。
