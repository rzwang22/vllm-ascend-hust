## 配置传递审计

1. core `SpeculativeConfig` 构造 `draft_model_config` 时，`enforce_eager` 取自 target。
   因此 graph target 下，speculative override 为 True 并不意味着原 draft ModelConfig 为 True。
2. speculator 的 `self.vllm_config` 是 target 配置，并将它传入 `load_dspark_model()`。
   旧 loader 校验这个 target 的 eager 标志，正是服务器首错。
3. 旧 `_build_draft_vllm_config()` 通过 `replace(VllmConfig)` 共享 model/compilation 等子配置。
   在这种共享配置上设置 eager 会污染 target；即使先复制再重建，完整平台校验也会重置
   进程级 Ascend 配置，并可能关闭 target 的 `npugraph_ex`。
4. 新 builder 复制已验证配置，不重新构造 VllmConfig。独立设置 runtime ModelConfig、
   draft ModelConfig 的 eager=True，以及 compilation mode/graph mode=NONE、capture sizes=[]。
   attention 按现有 NPU 平台规则归一化，并开启 non-causal；量化仍使用独立校验的 draft ModelSlim 配置。
   target-derived runtime ModelConfig 与另传给 `get_model()` 的 draft ModelConfig 保持原 core ABI，
   也不会重新从 callable `hf_overrides` 解析量化。
5. 仅共享 `static_forward_context` 和 `static_all_moe_layers` 活跃注册表，保持 KV/MoE 发现，
   不复制实际 target 权重或缓存。原 checkpoint sharing、TP8、EP、PP1、K=5、层号及量化检查保留。
6. `initialize_model()` 用 runtime VllmConfig 建立 current config 并调用模型构造函数；
   draft 包装类保存此配置。speculator 成功加载后采用其 eager draft ModelConfig，
   draft attention 初始化、正常 forward、profile forward 均使用同一隔离配置。
   两个 forward 仍显式设置 `cudagraph_runtime_mode=NONE`。
7. core runner 把 **target** graph mode 传给 `init_cudagraph_manager()`；
   speculator 只记录该请求，自身 mode=NONE、capture 为 no-op。target manager 独立 capture/replay。
   proposal ownership、KV 槽位、Markov/采样逻辑没有修改。

## capture shape 审计

core runner 的 `decode_query_len = K + num_new_sampled_tokens_per_step = 5 + 1 = 6`。
target verification 是每请求 6 tokens；draft 自身的 query 是每请求 5 tokens。
日志 `enable_sp=False`、`cudagraph_capture_sizes=[1,2,4]`、max size=4，不能覆盖 P1 verification。
core `adjust_cudagraph_sizes_for_spec_decode(6, 8)` 向上取整后受 max=4 截断，会报无有效尺寸。
这是 loader 修复后的后续覆盖问题，不能替代本次首错。

本次 P1 显式设置 `[6]`。后续 B=2/B=4 可用 `[6,12,24]`；若开启 SP，尺寸还需满足
`lcm(6,8)=24`，且 target graph descriptor 的请求数上限必须容纳相应 padding。
不能只看启动日志或 capture 完成；需核对 worker 实际 descriptor 和 measured FULL replay。
